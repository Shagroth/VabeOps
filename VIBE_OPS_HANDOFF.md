# Vibe Ops — Design Handoff
Версия 1.0 · результат DESIGN-режима по мастер-промпту v2.0 · 2026-11-12

Режим выполнения: **DESIGN**. Причина: мастер-промпт описывает полную IA-
и арт-дирекшн-переработку, отличную от текущей реализации (см. §0
«Текущее состояние»). Прежде чем переписывать живой задеплоенный MVP,
решение фиксируется здесь для подтверждения, а не применяется молча.

---

## 0. Текущее состояние (факт, не часть брифа)

На момент написания в репозитории уже есть работающий MVP:
Next.js + Prisma + Auth.js (email magic link) + Cloudflare R2.
Навигация сейчас: `/` (лендинг+вход), `/modules` (список), `/modules/[id]`
(урок+сдача+фидбек), `/admin` (создание когорт/модулей/вопросов фидбека/
созвонов). Нет версионирования сдач, нет раздела обсуждений/«Поток»,
нет отдельного «Обзор» с «следующим шагом», визуальный язык — дефолтный
Tailwind без выраженного арт-дирекшна.

Этот документ описывает целевое состояние. Раздел §11 отмечает, что
из этого меняет структуру данных, а что — только интерфейс поверх
существующих моделей.

## 1. Диагноз и допущения

**Диагноз.** Текущий MVP технически работает, но не рассказывает историю:
нет ощущения «авторской инженерной мастерской», нет сквозного учебного
цикла (только контент → сдача → фидбек, без явного «разбор решения» и
«изменились условия»), визуально неотличим от типового Tailwind-шаблона.

**Допущения (обратимые, явно помечены как гипотезы):**
- Длительность пилота — гипотеза 5 недель. Не факт, не публикуется как
  утверждённая программа участникам до решения автора.
- Недельная нагрузка, точные даты, тариф будущего потока — не определены,
  в прототипе показываются как плейсхолдеры/TBD, а не выдуманные числа.
- Расходы участников на сторонние AI-инструменты (API ключи и т.п.) —
  требуют отдельного уточнения в FAQ; в этой версии помечены как открытый
  вопрос, не скрыты и не декларированы как «всё включено».
- Кейс для сквозного сценария (п.4 брифа): **«Внести изменение в
  существующий сервис, не нарушив его контракт»** — один демонстрационный
  кейс, не обязательная тема всего курса.

## 3. Художественное направление: «Decision Trails»

**Концепция.** Визуальный мотив — развилка инженерного решения: точка
выбора → путь → проверка → (при изменении условий) новая развилка.
Мотив не иллюстрирует «магию ИИ» — он показывает структуру мышления.
Используется дозированно: hero-композиция, разделители недель в
программе, и как основа компонента «Разбор решения» (где это буквально
диаграмма выбора/альтернативы/проверки, а не декоративный узор).

**Принцип.** Выразительная публичная обложка + спокойное рабочее
пространство — hero/лендинг может быть смелым, уроки и практика —
нейтральны и ориентированы на чтение и код.

### Design tokens (гипотеза, подлежит пересмотру без потери смысла)

**Цвет (семантические роли):**
| Роль | Значение | Использование |
|---|---|---|
| `surface.hero` | `#14151A` (графитовый, тёплый подтон) | Hero лендинга, обложки программы |
| `surface.learning` | `#FAF7F1` (тёплый светлый) | Уроки, практика, рабочее пространство |
| `surface.card` | `#FFFFFF` на светлой / `#1C1E24` на тёмной | Карточки поверх базовой поверхности |
| `text.primary` | `#1A1A1A` светлая тема / `#F2F0EC` тёмная | Основной текст |
| `text.secondary` | `#6B6760` / `#A9A49C` | Вторичный текст, метаданные |
| `accent.action` | `#2F6FED` (холодный синий) | Основной CTA, ссылки, активные состояния |
| `accent.change` | `#E07A3F` (тёплый терракотовый) | «Изменились условия», предупреждения, needs-revision |
| `border.hairline` | `rgba(0,0,0,0.08)` / `rgba(255,255,255,0.12)` | Границы карточек, разделители |

Проверено на контраст: `text.primary` на `surface.learning` ≈ 15:1 (AA/AAA
для текста); `accent.action` (#2F6FED) на белом ≈ 4.6:1 — достаточно
для текста ≥18px/жирного 14px и для UI-компонентов, но **для обычного
14px текста нужен более тёмный оттенок акцента** (например `#1E54C7`)
— зафиксировать при реализации, не полагаться на эту оценку как финальную.

**Типографика:**
- UI/текст: Inter (хорошая поддержка кириллицы) или системный sans-serif
  аналог как fallback.
- Код/метки: JetBrains Mono — только код, технические бейджи, timestamp.
- Шкала (base 16px, учебный текст может быть 18px для длинного чтения):
  `12 / 14 / 16 / 18 / 22 / 28 / 36 / 48` px, модульный шаг ≈1.25.
- Длина строки для учебного текста: 65–75 символов — ограничить
  max-width контентного блока (`~680px` при 18px).

**Пространство и форма:**
- Базовая единица 4px: отступы `4/8/12/16/24/32/48/64`.
- Радиусы — ограниченное семейство: `6px` (инпуты, кнопки, бейджи),
  `12px` (карточки, модалки). Не вводить третий радиус без причины.
- Elevation — почти плоский дизайн; один уровень тени только для
  модалок/поповеров (`0 8px 24px rgba(0,0,0,0.12)`), карточки — через
  `border.hairline`, не через тень.
- Focus — видимое кольцо `2px accent.action`, offset `2px`, никогда
  не убирается через `outline: none` без замены.
- Motion — 150–200ms ease-out для смены состояния (например черновик →
  отправлено); `prefers-reduced-motion` отключает неэссенциальную
  анимацию, оставляя мгновенную смену состояния.

## 4. Архитектура пилота и сквозной сценарий

**Два уровня:** PUBLIC (лендинг, заявка) и WORKSPACE (обучение).

**IA Workspace:** `Обзор` / `Программа` / `Практика` / `Поток`.
Профиль — в меню пользователя. Управление потоком — отдельный раздел,
виден только автору (соответствует текущему `/admin`, переосмысленному
как «Рабочее место автора», см. §8 брифа).

**Сквозной сценарий (прототипный маршрут):**
```
Лендинг → Программа → Заявка на пилот
                                   │
                    (демовход приглашённого участника)
                                   ▼
Обзор (следующий шаг) → Открытая неделя → Урок → Практика
      → Сдача результата → Отзыв автора → Исправленная версия
                                   │
                              Поток (созвоны + контекстное обсуждение)
```

Заявка **не** становится автоматическим доступом — это разные состояния,
явно разведённые в прототипе (как того требует §9 брифа).

## 5. Спецификация пяти ключевых экранов

Для каждого: иерархия → пример текста → CTA → состояния → desktop/mobile →
компоненты. Тексты — рабочие примеры для прототипа, не финальный копирайт.

### 5.1 Лендинг (PUBLIC)

**Иерархия:** Hero (обещание+аудитория+статус пилота+CTA) → «Разбор
решения» (конкретный пример вместо абстрактного обещания продуктивности)
→ Результаты по неделям (гипотеза 5 недель, результат+артефакт, не только
название технологии) → Формат (3 встречи) → Автор → Требования → FAQ →
Заявка.

**Пример текста hero:**
> Работай с AI-агентами. Думай как инженер.
> Когортный пилот для разработчиков, которые уже пишут код и хотят
> осмысленно встраивать агентов в реальную работу — без потери контроля
> над качеством и рисками.
> **Бесплатный пилот · 5–10 мест**

**CTA:** основной — «Подать заявку на пилот»; вторичный — «Посмотреть
программу»; третий, визуально тише — «Войти» (для уже приглашённых).

**Состояния:** заявка не отправлена / отправлена (ясный экран «что дальше»,
без выдуманных сроков ответа) / режим демо (баннер «это демонстрация,
заявка не уходит реальному автору» — обязателен по §6 брифа).

**Desktop/mobile:** hero на мобильном — вертикальный стек, иллюстрация
Decision Trail уменьшается до одной развилки (не теряет смысл при
сжатии). Программа недель — горизонтальные карточки на desktop,
вертикальный список на mobile.

**Компоненты:** `HeroPromise`, `DecisionBreakdownTeaser` (превью
разбора решения), `WeekResultCard`, `AuthorCredibility`, `ApplyForm`
(имя/контакт/опыт с агентами/рабочая задача — GitHub/LinkedIn опционально).

### 5.2 Обзор (WORKSPACE)

**Иерархия:** один доминирующий блок «Следующий шаг» → текущая неделя →
ближайшая встреча → фидбек, требующий внимания. Не восемь карточек
статистики.

**Логика «следующего шага» (состояния, не опционально):**
новичок → онбординг; есть начатый урок → «Продолжить»; материал пройден
→ «Перейти к практике»; работа на доработке → открыть комментарий;
всё актуальное завершено → «Ждём открытия следующей недели, дата X»
(не наказывающий тон при отставании — например «Неделя 2 всё ещё
открыта, продолжай в своём темпе»).

**Пример текста (состояние «нужна доработка»):**
> Практика недели 2 требует доработки. Автор оставил комментарий к
> твоей сдаче — загляни, когда будет время.

**Desktop/mobile:** блок «Следующий шаг» — на всю ширину на mobile,
на desktop — 2/3 ширины с ближайшей встречей в сайдбаре справа.

**Компоненты:** `NextStepCard` (вариативный по состоянию), `WeekSummary`,
`UpcomingSessionCard`, `FeedbackAlert`.

### 5.3 Урок / Неделя (WORKSPACE)

**Иерархия:** Курс → недели → материалы+практика (без лишнего уровня
«модуль» внутри недели — соответствует текущей модели `Module`).
Урок: цель → видео ИЛИ материал (видео не единственный способ понять
содержание — конспект обязателен, видео опционально, что уже верно
в текущей реализации `notesMd`+`videoKey`) → код/ссылки → связанная
практика → контекстный вопрос → следующее действие.

**Доступность будущих недель:** тема/результат/дата открытия видны,
содержимое — нет, если неделя не открыта. **Важно:** просмотр материала
≠ доступность модуля ≠ сдача практики — три разных состояния, не
смешивать (opt-in unlock, не как сейчас «весь контент открыт сразу» —
см. §11 про то, что это решение пилота, не архитектурное ограничение).

**Пример текста (недоступная будущая неделя):**
> Неделя 3 · Мультиагентные системы
> Открывается 18 ноября. Результат недели: собрать простую
> мульти-агентную связку и объяснить, когда она оправдана.

**Desktop/mobile:** видео/код — full-width на mobile со свайпом между
вкладками «Конспект»/«Код»; на desktop — side-by-side.

**Компоненты:** `LessonHeader`, `VideoOrNotes`, `CodeBlock`,
`LinkedPracticeCard`, `NextActionBar`.

### 5.4 Практика + Отзыв (WORKSPACE)

**Иерархия:** Контекст и ограничения → ожидаемый результат и критерии
приёмки → стартовые материалы → поле сдачи (ссылка на результат) →
короткий «Разбор решения» → история версий и фидбека.

**Состояния (обязательный набор):** не начато → черновик → отправлено →
нужна доработка → принято. Новая версия сдачи не удаляет историю
предыдущего фидбека — видна лента версий.

**Разбор решения (компонент A из брифа) — структура полей:**
задача; выбранный подход; отвергнутая альтернатива и причина; способ
проверки; ограничение/риск; условие пересмотра. Визуально — мини-диаграмма
Decision Trail (точка выбора → путь → проверка), не форма из шести
безликих textarea.

**Изменились условия (компонент B) — пример текста:**
> Условия изменились: инструмент теперь работает в режиме read-only.
> Как это меняет твой подход? Что в уже сделанном решении нужно
> пересмотреть?

**Приватность по умолчанию:** работа видна участнику и автору;
публикация в «Поток» — осознанное отдельное действие с предупреждением
не публиковать секреты/закрытый код.

**Desktop/mobile:** лента версий сдачи — collapsed по умолчанию на mobile
(показывается только последняя + счётчик «ещё 2 версии»).

**Компоненты:** `PracticeBrief`, `SubmissionForm` (уже есть, расширить
версионированием), `DecisionBreakdownForm`, `ConditionsChangedPrompt`,
`FeedbackThread`, `SubmissionStatusBadge`.

### 5.5 Поток (WORKSPACE)

**Иерархия:** Встречи (kickoff/midpoint/final — уже есть `LiveSession`)
→ участники (профиль отвечает «что делает/исследует/где может помочь»,
без рейтинга активности) → контекстные обсуждения, привязанные к
неделе/уроку/работе (не отдельная лента).

**Пример текста карточки встречи:**
> Midpoint · 25 ноября, 19:00 (твой часовой пояс: MSK)
> Разбор затыков половины группы + живой фидбек.
> [Присоединиться] · Материалы появятся после недели 4.

**Состояния:** встреча предстоит / идёт сейчас / запись ожидается /
запись доступна — не выдумывать «запись доступна», если её ещё нет.

**Desktop/mobile:** список участников — grid 3 колонки desktop,
список mobile; обсуждения — тред, привязанный к карточке урока/работы,
открывается инлайн, не как отдельная страница форума.

**Компоненты:** `LiveSessionCard`, `ParticipantCard` (что делает/
исследует/чем может помочь — три коротких поля, не биография),
`ContextualThread`.

## 6. Граница MVP и порядок реализации

**Уровень A (прототип/демо):** фикстуры, localStorage для демо-прогресса
и демо-сдач, явный баннер демо-режима, сброс демо-состояния кнопкой.
**Уровень B (реальный пилот — уже частично есть):** серверные проверки
доступа, реальное сохранение (Postgres — уже есть), обработка заявок
(ещё нет формы заявки — сейчас вход сразу по приглашению через magic link
без отдельной стадии «заявка/приём»).
**Уровень C (будущая коммерческая платформа):** оплата, мультиарендность
по тарифам — осознанно не делаем сейчас.

**Что меняет модель данных (не только UI):**
- Версионирование `Submission` (сейчас один `upsert` перезаписывает —
  нужна история версий + привязанный тред фидбека).
- Поля для «Разбор решения» и «Изменились условия» — структурированные
  поля в задании/сдаче, не просто свободный markdown.
- Форма заявки + состояние «заявка подана, не зачислен» отдельно от
  `Enrollment` — сейчас такой промежуточной стадии нет.
- `unlock_at`/дата открытия недели — в MVP сознательно убрано (контент
  открыт сразу), в этом брифе возвращается как явное состояние §5.3.
  **Это расхождение с решением пилота, принятым раньше в разговоре —
  требует явного подтверждения, не меняется автоматически.**

**Порядок реализации (BUILD, после подтверждения направления):**
1. Визуальный язык и токены (Tailwind theme, типографика, базовые
   компоненты кнопок/карточек/бейджей состояний) — на существующих
   страницах, без смены IA.
2. Обзор + логика «следующего шага» — новая страница, использует
   существующие модели.
3. Разбор решения + версии сдачи — требует миграции схемы Prisma.
4. Поток (обсуждения) — новая сущность, самый дорогой кусок по данным.
5. Заявка/приём — отдельная стадия до Enrollment.
6. Decision Trail как визуальный мотив hero/лендинга — можно делать
   параллельно с п.1, независимо от остального.

**Критерии приёмки (выборочно, полный список — §12 брифа):**
посетитель за 10 секунд понимает аудиторию/формат/статус пилота;
новый участник находит следующий шаг без объяснений; отправленная
работа не теряет историю фидбека при новой версии; пустой «Поток»
выглядит намеренно (есть обсуждение, подвязанное к текущей неделе),
а не как заброшенная соцсеть.

## 7. Открытые вопросы — решено автором (2026-11-12)

- **Открытие недель:** реализовано как ручной тумблер `isOpen` на
  модуле (не дата-лок). Админ сам щёлкает, когда открыть следующую
  неделю; студент видит закрытую неделю затемнённой с пометкой
  «скоро откроется». Это НЕ `unlock_at` из брифа — проще, без часовых
  поясов и автоматики, осознанно для масштаба пилота.
- **Заявка → приём:** реализовано. `/apply` (публичная форма) →
  `Application` со статусом PENDING → `/admin/applications` (Принять/
  Отклонить). Принятие НЕ создаёт доступ автоматически — зачисление
  в `Enrollment` по-прежнему отдельный ручной шаг после реального
  входа участника по magic link. Разводит «заявка» и «доступ», как
  требовал бриф §9.
- **Тариф будущего потока:** осознанно не определяется сейчас,
  решится после пилота. Пилот — бесплатный.
- **Стоимость сторонних AI-инструментов:** не драматизируем — в этой
  конкретной пилотной группе у всех уже есть свои подписки/доступ к
  AI-инструментам. Одна тихая строка на `/apply` фиксирует это как
  факт («доступ — свой, за твой счёт»), без объёмного дисклеймера.
  Для будущих потоков с более широкой/незнакомой аудиторией вопрос
  может потребовать более заметного места — не факт на сейчас.

## 7a. Выполнено после этого хендоффа

- Статусы сдачи (SUBMITTED/NEEDS_REVISION/ACCEPTED) + версионирование +
  «Разбор решения» + «Изменились условия» реализованы (шаг 3).
- «Поток» реализован (шаг 4): участники пишут короткий профиль (делает/
  исследует/может помочь — без рейтинга активности), обсуждения
  привязаны к модулю/неделе (не отдельная лента), `/stream` агрегирует
  созвоны + последние обсуждения. Добавлен общий `WorkspaceNav`
  (Обзор/Программа/Поток) вместо разрозненных ссылок по страницам.
  **Отклонение от брифа:** отдельной страницы «Практика» в навигации
  нет — статус сдачи показывается прямо в `/modules` (бейдж на
  карточке недели), четвёртый экран дублировал бы его же. Осознанное
  упрощение под масштаб пилота, не забытый пункт.
- Визуальные токены Decision Trails применены к публичной воронке
  (лендинг + `/apply`): Inter/JetBrains Mono, тёплая светлая
  поверхность по умолчанию, тёмный графитовый hero с минимальным
  мотивом развилки, `accent-action` для основных CTA. Проверено
  скриншотами через Orca browser (desktop viewport).
  **Не тронуто:** `/modules`, `/admin/*` всё ещё на дефолтных
  Tailwind-токах с системным `dark:` — это следующий шаг, не часть
  этого прохода, чтобы не переписывать слишком много за один раз.
